# SOP：Worker 安全边界与额度加固

**状态：待实施。** 本文是改造、验收和发布计划，不代表线上已启用。常规运维见 [运维手册](sop.md)，额度口径见 [额度设计](quota.md)。本方案保留 **Worker + Static Assets + D1**，不以迁库、Durable Objects、Queues 或 R2 为前提；涉及安全控制的回滚以本文为准，不恢复默认透传或无额度运行。

## 1. 发布顺序和门槛

| 批次 | 改动 | 执行 / 验收 | 放行条件 |
|---|---|---|---|
| S1 代理收口 | 按方法、路径和字段放行；文件校验归属；停止旧入口 | Worker 开发 / 前端验收人 | 纯文本聊天可走模拟上游；禁用操作没有上游调用 |
| S2 身份与隔离 | 原子兑换、登录限流、会话撤销；补齐 D1 写入归属 | Worker 与前端开发 / 数据验收人 | 登录、封禁和数据隔离回归通过；已确认旧会话切换方案 |
| S3 成本控制 | 原子预占、流式结算、异常回收、对账和停流开关 | Worker 开发 / 运维验收人 | 模拟账本回归通过后才放行真实上游冒烟；完成账单对账后才扩大发码 |

小团队可以一人承担多个角色，但每批都要记录实际执行人、验收结果和回退目标。S1/S2 完成而 S3 未完成期间，保留模拟上游或关闭真实付费入口；不以人数作为安全门槛。

## 2. 开工前：锁定基线

1. 记录 Git 基线、当前部署版本、环境和 D1 绑定。核对 [Worker 配置](../worker/wrangler.toml) 和实际 Cloudflare 配置；不要把运维历史里的版本号当作当前线上版本。
2. 盘点 [聊天客户端](../web/src/services/api/client.ts)、[语音客户端](../web/src/services/api/speech.ts) 和 [同步客户端](../web/src/services/chat/sync.ts) 的真实请求，登记每个操作的调用方、必要性、认证、数据归属、请求体上限和计费口径。发布前同步隐藏被关闭的入口或给出明确提示。
3. 准备独立预发 Worker、D1、凭证和模拟上游；测试数据库用合成数据，不复制生产聊天记录。模拟上游记录调用数，并可返回完整 SSE、缺失 usage、超时和错误。先记录基线，再在改造后的实现上跑验收；不在生产验证边界缺陷。
4. 所有数据变更走新增结构 → 验证 → 切换 → 延后清理。用独立本地库从现有迁移初始化并重放新迁移；生产变更前按 [运维手册](sop.md) 导出备份、在隔离库验证恢复。备份放仓库外的受控位置，不随提交或构建发布。

## 3. S1：代理默认关闭，按功能开放

1. 改造 [Worker 路由](../worker/src/index.js)：上游操作用明确的路径和 HTTP 方法匹配；未登记路径返回 `404`，已登记路径的方法不符返回 `405`。固定 DeepSeek 出站地址和目标路径；不转发未声明的请求头、查询参数或请求字段。上游错误转换为本地错误码和请求 ID，响应头按需选取，不复制上游正文或凭证。浏览器同源为默认；没有明确调用方时移除通配 CORS。
2. 首发只启用 `POST /anthropic/v1/messages`；`GET /models` 确认有调用方后再保留。服务端继续固定模型，并限制消息体、上下文及最大生成量；未能给出成本上界的工具参数默认关闭。旧 `/api/chat`、文件和语音入口保持关闭，待逐项验收后再启用。
3. 文件若必须恢复，在 D1 保存本地文件标识、所有者和上游 ID；上传只有归属记录落库后才向客户端发布标识。删除、查询和**聊天正文里引用文件**均要按当前用户查找，再由 Worker 替换成上游 ID。无可靠归属的旧文件要求重新上传；归属写入失败则记录待清理对象。按实际读取字节限制上传，不以 `Content-Length` 为唯一依据；如果供应商可能部分接收并产生费用，需纳入清理和对账。
4. 前端统一验证 Markdown、搜索与附件外链；审查 Mermaid/KaTeX 等 HTML 输出，先用预发验证 CSP，再对生产执行策略。附件、语音不与文本聊天捆绑上线。

**验收：** 模拟上游只收到明确启用的正常操作；关闭的功能在界面有明确状态；文件恢复前，用合成资源验证归属策略，确认未知或非本人资源不会发往上游；浏览器不接收上游凭证和原始错误。

## 4. S2：兑换一次、会话可撤、写入带归属

1. 邀请码兑换在同一事务性批次内校验未使用和未过期、记录兑换、创建用户。账号创建只能随兑换成功发生；仅把两条无条件 SQL 放进同一个批次不算完成。新码使用密码学随机值，服务端存摘要；登录在边缘配置按来源限流，并在应用内对兑换做独立节流。错误和日志里不出现邀请码原文。
2. 将 Web 登录切换到同源的可撤销会话：服务端保存会话凭证摘要、用户、到期与撤销状态；浏览器使用 `Secure`、`HttpOnly`、适当 `SameSite` 的 Cookie，并对写操作校验来源和 CSRF。退出撤销当前会话，封禁拦截该用户所有会话；不再接受无限期过期 Token 续签。前后端同批发布；优先让现有用户在切换点重新登录，并提前准备能保留原 `user_id` 的一次性迁移/恢复方式，避免重建账户导致历史丢失。切换后清理旧 LocalStorage 凭证。
3. 会话、消息和用量请求由认证上下文确定用户。把归属条件写入实际 D1 写操作及同一批次，不用异步的前置查询代替；必要时用含租户标识的复合键。幂等记录至少按用户与操作隔离，并校验同一键的请求语义一致。旧用量数据保留供对账；切换前先处理在途请求，避免新旧实现各结算一次。

**验收：** 同批兑换回归中，一张可用邀请只生成一个账号；过期邀请不生成账号；退出后该会话立即失效；封禁不影响其他账号；原账号历史在重新登录后仍可读；在合成双用户数据上验证私有资源隔离、写入所有权约束和请求标识隔离。

## 5. S3：请求先预占，结算可追踪

1. 汇总所有可产生上游成本的操作：文本、按开关开放的搜索、文件和语音。为每类定义受服务端约束的最大成本，按最保守适用单价估算；无法测量或无费用上限的操作不开放。预发先校验价格单位、最小计费单位和第三方账单口径。
2. 保留 D1 作为起点：在同一事务性操作内校验剩余额度、并发/频率上限，建立请求与预占记录；成功后才发出上游请求。加全站停流开关和独立支出上限；若上游支持硬预算，同时配置，区分真实账单上限和站内虚拟额度。D1 不可用时停止新的上游调用。
3. 请求状态至少区分 `reserved`、`settled`、`released`、`reconcile_required`。结算按实际 usage 扣减并释放剩余预占，余额、流水和请求状态同事务更新；重复结算不得二次扣账。明确未发出的请求可释放；断流、超时或 usage 缺失不按零费用处理，先进入待对账，保留对应风险预算。清理定时任务分批执行并记录失败，回收和结算竞争只能由一个状态转换成功。已有额度 cron 与新版账本切换需约定唯一写入者。
4. 监控按路由记录上游调用数、被拦截请求、5xx、预占滞留、待对账金额和上游账单差额；日志只保留必要的请求标识、状态和计量，不保存 Token、用户正文或附件内容。预发演练停流，并确认停流期间仍可处理结算、查看历史和对账。

**验收：** 用模拟上游覆盖余额不足、受限并发、正常 SSE、断开、缺失 usage、重复结算和定时任务重试。放行门槛：没有预占就没有出站调用；一笔请求至多扣一次；没有负的可用额度；未结算费用可定位，不会被静默清零。通过后才使用专用低预算凭证做正常功能冒烟；待该笔账单或用量凭据可核对后再扩大发码。若供应商不提供足够细的对账字段，先记录差额处理办法，暂不开放无法核算的付费功能。

## 6. 发布、暂停与回退

每批按 **本地回归 → 独立预发 → 备份与只增迁移 → 发布 → 正常功能冒烟 → 观察与登记** 执行。以下是仓库根目录的基础检查，不能代替新增测试和预发验收：

```powershell
git status --short
node --check worker/src/index.js
if ($LASTEXITCODE -ne 0) { throw 'Worker syntax check failed' }
Push-Location web
try {
    pnpm run type
    if ($LASTEXITCODE -ne 0) { throw 'Type check failed' }
    pnpm run lint
    if ($LASTEXITCODE -ne 0) { throw 'Lint failed' }
    pnpm run build
    if ($LASTEXITCODE -ne 0) { throw 'Build failed' }
} finally {
    Pop-Location
}
```

发布操作按 [运维手册](sop.md)；第一次仅向指定验收账号开放正常能力。观察至少 30 分钟，并确认至少一次适用的清理任务运行结果；计费功能还要等首批用量完成对账。遇到未通过授权的上游调用、归属异常、重复扣费或无法解释的账差，立即停止扩大范围并关闭受影响入口；如怀疑凭证泄露，按运维手册轮换并撤销受影响会话。

回退优先关闭新增能力，继续保留白名单、会话撤销和账本保护。只有上一版本仍兼容当前结构且不放宽已收紧的边界，才回退 Worker 版本；否则保持付费入口关闭并向前修复。**不要以 `QUOTA_MODE=off` 恢复服务，也不要用旧数据库整库覆盖正在使用的新账本。** 保留待对账记录和流水；确认在途结清后再做恢复或数据修正。
